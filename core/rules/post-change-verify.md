# Final-candidate verification

Once the code is stable, run one round of objective verification over the final source, covering this change: the project's existing cheap lint / check → a build covering the production entry point → the narrowest relevant tests when the user asks, the plan specifies them, or existing tests directly cover the change. When project rules specify more concrete commands or scope, follow the project; simulator, real device, and full test suites run only when the user asks or the corresponding skill triggers them. Root picks the test scope and writes the full command, then always hands it to `command-runner` (model and effort follow that agent's definition). Run commands with `set -o pipefail`, `tee` the full output to a temporary log first, then pass it through a filter to shorten it (for `xcodebuild`, pipe into `xcbeautify` and add `-resultBundlePath`); Root reads the result block first and, when the summary is in doubt, reads the log / result bundle directly instead of re-running. Other long commands can go to `command-runner` as well.

- On failure, first separate a regression from this change, a pre-existing problem, and an environment problem; fix only the scope the evidence hits. After a source change, re-run from the earliest invalidated check.
- When the same diagnosis makes no progress twice in a row, stop and ask the user; do not fix blindly.
